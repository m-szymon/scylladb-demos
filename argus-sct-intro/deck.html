Argus tracks. Jenkins executes. SCT reports.

The executor. A folder of jobs, each a jenkinsfile from the SCT repo. A build runs hydra on a runner and passes parameters as environment.

The test itself, on cloud machines. Uses the Argus client from the repo to send events, results and log archives while running.

db · loaders · monitor

events, results, logs, status, straight from the run

A run in Argus and a build in Jenkins are the same thing seen from two sides. The Jenkins link on the run header takes you across.

Three boxes, two directions. Left to right is control: Argus triggers a Jenkins build with parameters, the build runs SCT inside hydra. Right to left is reporting: SCT talks to Argus directly during the run, not through Jenkins. That is why a run can show events and partial results while Jenkins still says in progress.

Part 2 · under the hood

A Jenkins job is a small file in the SCT repo

jenkins-pipelines/oss/longevity/longevity-10gb-3h.jenkinsfile

longevityPipeline(
  backend: 'aws',
  region: 'eu-west-1',
  test_name: 'longevity_test.LongevityTest.test_custom_time',
  test_config: 'test-cases/longevity/longevity-10gb-3h.yaml',
)

That is the whole job: which shared pipeline, which backend, which test class, which YAML. The Argus test is a page that points at this job.

What the pipeline does on every build

1

Create the run in Argus

2

Create an SCT runner VM in the cloud

3

Run hydra there with the job’s settings plus yours

4

Collect logs, clean up resources

5

Report final status to Argus and by e-mail

Steps 4 and 5 run even when the test fails or is aborted.

Shared pipelines live in vars/ in the SCT repo. More in docs/sct-pipelines.md.

The one idea: a job is a few lines that bind a pipeline template to a test class and a YAML. Argus adds a page on top of it: it discovers jobs from Jenkins, and the folder definitions file next to the jenkinsfiles tells it which plugin and which Run wizard to use. Clone in Argus goes the other way: it creates a new Jenkins job from an existing one, and the page comes with it. The numbered list is what happens when you press Run, and the runner in step 2 is why a Jenkins run has no laptop involved. The jenkinsfile snippet is simplified; open the real file if someone asks.

Part 3 · SCT

One SCT run, end to end

Runner

Hydra container. Runs the test class, drives everything over SSH.

DB cluster

ScyllaDB nodes under test, plus any sidecar the test needs.

Loaders

cassandra-stress, latte, scylla-bench, ycsb.

Monitor

Scylla Monitoring stack for the cluster and loaders.

Shared

Argus, S3 for logs, Elasticsearch, cloud account.

runner reports events, results and log archives

provision

install + configure

run workload

inject faults

collect logs

tear down

The SCT README has a generated system map per test type (docs/system-map) that shows exactly this for performance, longevity, upgrade and others.

Everything a run needs is created by the run and destroyed at the end. The runner is the only piece that runs SCT code; the rest are plain machines it drives over SSH, and the runner is also the one talking to Argus and S3. Faults are nemesis, used by longevity tests and usually skipped by performance tests. If time allows, open the interactive system map from the repo.

Part 3 · SCT

Three ways to run a test

In the cloud

Argus or Jenkins

Run button in Argus, or Build with parameters in Jenkins. A runner VM is created next to the cluster. Results tracked in Argus.

Where to look while it runs: the Jenkins console first, then the Argus run as events arrive.

Needs

  • Argus and Jenkins accounts
  • Nothing on your machine

From your laptop, cloud backend

hydra run-test

Your checkout, your branch, real cloud machines. Hydra runs the test locally over public IPs, or on a runner you create in the cloud, which makes it the same as a Jenkins run.

Needs

  • Docker or Podman, AWS access via Okta
  • Cloud credentials for the backend
  • Clean up when done, it costs money

Fully local

docker or minicloud

Docker backend: cluster as containers, fastest for test logic. Minicloud: emulates EC2 and GCE APIs with KVM guests, so the real aws and gce code paths run.

Needs

  • Docker, passwordless sudo, AWS access for S3
  • Minicloud: KVM, about 22 GiB RAM, 80 GiB disk

Every way needs AWS access, even the local ones: SCT reads SSH keys and credentials from S3. Local results land in ~/sct-results/latest. Set SCT_ENABLE_ARGUS=false for local experiments.

Walk left to right. The middle column is the bridge: the same hydra command Jenkins runs, from your checkout. Without a runner, add the public-IP network config from the README table. With hydra create-runner-instance and execute-on-runner you get the Jenkins setup with your branch. Right column is where test logic gets debugged for free.

BackendWhat it isNotes
aws · gce · azure · ociPublic clouds, real VMsaws most used, gce for artifacts and upgrades. From a laptop add the public-IP network config.

Per-backend settings and docs: README section 3 and docs/configuration_options.md.

Do not read the table aloud. Point at the command on top: the backend is a flag plus credentials, everything else in the test stays the same. Mention that minicloud is not a backend name but a way to run the aws or gce backend locally.

Part 3 · SCT

What do I touch? Start at the top

Change a value, same test

Env var in Argus, or edit the YAML

Duration, config path, versions, node counts. No code, no new job.

New variant of an existing test

New test-case YAML

A new YAML under test-cases and a jenkinsfile pointing at it. Or clone the job in Argus and override values.

New behaviour or new result

New or changed test class

Python, unit tests, a jenkinsfile, an Argus page. Follow docs/writing-a-test.md.

Checklist for a new test: test class, YAML with test_metadata, jenkinsfile, Argus page, unit tests, docs.

Most requests from the team will be the first row. Make that explicit so people do not open the Python when they only need a value changed. The third row is the only one that needs a review from the SCT maintainers.
